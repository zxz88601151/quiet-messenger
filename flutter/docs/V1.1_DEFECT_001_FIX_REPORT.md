**日期**: 2026-08-24
**缺陷编号**: DEFECT-001
**状态**: FIXED
**范围**: 仅修复 DEFECT-001，不涉及其他生产代码变更

---

## 1. Defect Description

### 标题

`EventEnvelope.fromJson` 对非 String 类型的 `type` 字段抛出未捕获 `TypeError`，异常逃逸到 RealtimeClient 的 stream onData 回调所在的 Dart zone。

### 触发条件

服务端发送 JSON 消息，其中 `type` 字段为非 String 且非 null 的值：

```json
{"type": 123}
```

### 影响

- 异常在 stream `onData` 回调中被 zone 报告为 uncaught error
- 客户端 subscription 不被取消（`cancelOnError: false`），state 保持 connected
- 后续合法消息仍可正常处理
- 但 uncaught error 在生产环境可能导致 crash 或被全局错误处理器捕获，属于真实生产代码缺陷

---

## 2. Root Cause

### 根因位置

`lib/core/realtime/event_envelope.dart` — `EventEnvelope.fromJson`

### 原始代码

```dart
factory EventEnvelope.fromJson(Map<String, dynamic> data) {
  return EventEnvelope(
    type: data['type'] as String? ?? '',  // ← 对非 String 值抛出 TypeError
    id: data['id'] as String? ?? '',
    timestamp: data['timestamp'] as String? ?? '',
    payload: (data['payload'] as Map<String, dynamic>?) ?? <String, dynamic>{},
  );
}
```

### 问题分析

`data['type'] as String?` 使用 Dart `as` 强制类型转换。当 `data['type']` 为 `int`（如 `123`）、`Map`（如 `{}`）或 `List`（如 `[]`）时，`as String?` 抛出 `TypeError`（运行时类型转换失败）。

该异常**不在** `RealtimeClient._onMessage` 的 try-catch 范围内——try-catch 仅包裹 `jsonDecode`：

```dart
void _onMessage(dynamic raw) {
  late final Map<String, dynamic> data;
  try {
    data = jsonDecode(raw as String) as Map<String, dynamic>;
  } catch (_) {
    return;  // 仅捕获 jsonDecode 异常
  }
  final evt = EventEnvelope.fromJson(data);  // ← 无 try-catch，异常逃逸
  ...
}
```

## 4. Fix Strategy

### 设计原则

1. **最小修改**: 仅修复 `type` 字段的类型安全问题，不改变其他字段解析逻辑
2. **类型安全**: 使用 `is!` 显式类型检查替代 `as` 强制转换
3. **符合现有协议语义**: `type` 为 null（缺失）时保留原有默认 `''` 行为；非 null 且非 String 时视为 malformed
4. **特定异常捕获**: 在 `_onMessage` 中仅捕获 `FormatException`，不吞掉所有异常
5. **与现有 malformed 处理一致**: 静默忽略（return），与非 JSON、非 Map JSON 的处理方式相同
6. **不改变正常 EventEnvelope 行为**: 合法 String type 的解析路径完全不变

### 为什么不在 fromJson 中直接 `toString()`

将 `123` 转为 `"123"` 会改变协议语义——服务端发送 `{"type": 123}` 是非法协议消息，不应被静默转换为合法 type `"123"` 后分发。正确行为是视为 malformed event 并忽略，与现有非 JSON 消息处理一致。

### 为什么用 `FormatException` 而非自定义异常

- `FormatException` 是 Dart 标准库异常，语义为"数据格式不符合预期"，完全匹配此场景
- 不需要新增自定义异常类，最小化变更
- `_onMessage` 中 `on FormatException` 精确捕获，不影响其他异常类型

## 5. Code Changes

### 5.1 EventEnvelope.fromJson (`lib/core/realtime/event_envelope.dart`)

**修改前**:
```dart
factory EventEnvelope.fromJson(Map<String, dynamic> data) {
  return EventEnvelope(
    type: data['type'] as String? ?? '',
    id: data['id'] as String? ?? '',
    timestamp: data['timestamp'] as String? ?? '',
    payload: (data['payload'] as Map<String, dynamic>?) ?? <String, dynamic>{},
  );
}
```

**修改后**:
```dart
factory EventEnvelope.fromJson(Map<String, dynamic> data) {
  final dynamic type = data['type'];
  // type 为 null（字段缺失）时兼容默认空字符串，与既有行为一致；
  // 非 null 且非 String（如 int / object / array）时视为 malformed envelope，
  // 抛出 FormatException 由调用方捕获并静默忽略。
  // 修复 DEFECT-001：原 data['type'] as String? 对非 String 值抛出未捕获 TypeError。
  if (type != null && type is! String) {
    throw FormatException(
      'EventEnvelope.type must be a String or null, got ${type.runtimeType}',
    );
  }
  return EventEnvelope(
    type: type as String? ?? '',
    id: data['id'] as String? ?? '',
    timestamp: data['timestamp'] as String? ?? '',
    payload: (data['payload'] as Map<String, dynamic>?) ?? <String, dynamic>{},
  );
}
```

**关键变更点**:
- 新增 `type != null && type is! String` 类型安全检查
- 非 null 非 String 时抛出 `FormatException`（含具体 runtimeType 便于调试）
- null 时走原有 `type as String? ?? ''` 路径，行为不变
- `id`、`timestamp`、`payload` 字段解析逻辑**未修改**

### 5.2 RealtimeClient._onMessage (`lib/core/realtime/realtime_client.dart`)

**修改前**:
```dart
final evt = EventEnvelope.fromJson(data);
onEvent?.call(evt);
```

**修改后**:
```dart
// EventEnvelope.fromJson 对非法字段类型（如 type 为 int/object/array）抛出
// FormatException。捕获后视为 malformed event 静默忽略，不让异常逃逸到 stream
// zone（DEFECT-001 修复）。仅捕获 FormatException，不吞掉其他未知异常。
final EventEnvelope evt;
try {
  evt = EventEnvelope.fromJson(data);
} on FormatException {
  return;
}
onEvent?.call(evt);
```

**关键变更点**:
- 使用 `try { ... } on FormatException` 精确捕获，**不使用** `catch (_)` 吞掉所有异常
- 捕获后 `return`（静默忽略），与上方 `jsonDecode` 失败的处理方式一致
- 注释明确说明修复原因和捕获范围

## 7. Post-Error Recovery Test

这是本缺陷最重要的回归验证：**非法消息不能影响后续合法消息处理**。

### 测试流程

```
1. 客户端连接并 ready（state = connected）
2. 发送 malformed event（{"type": 123}）
3. 验证：state 仍为 connected，事件未被分发，无 uncaught error
4. 发送合法事件（{"type": "message.new", "id": "msg_after_malformed", ...}）
5. 验证：合法事件被正确处理（type/id/payload 全部正确）
6. 再发一个合法事件
7. 验证：第二个合法事件也被正确处理
8. 全程无 uncaught error
```

### 关键断言

```dart
// malformed 后客户端存活
expect(localClient.state, ConnectionState.connected);
expect(localEvents, isEmpty);

// 合法事件被正确处理
expect(localEvents.first.type, 'message.new');
expect(localEvents.first.id, 'msg_after_malformed');
expect(localEvents.first.payload['text'], 'still works');

// 持续正常
expect(localEvents.last.type, 'second.valid');

// 全程无 uncaught error
expect(uncaughtErrors, isEmpty);
```

## 11. Remaining Known Defects

### DEFECT-002 (deferred): id / timestamp 字段同样使用 `as String?` 模式

**位置**: `lib/core/realtime/event_envelope.dart` — `EventEnvelope.fromJson`

**描述**: `id` 和 `timestamp` 字段使用 `data['id'] as String? ?? ''` 和 `data['timestamp'] as String? ?? ''`，与修复前的 `type` 字段模式相同。如果服务端发送 `{"type": "valid", "id": 123}`，`id` 字段的 `as String?` 会抛出 `TypeError`，同样逃逸到 stream zone。

**复现**:
```dart
factory.channels.first.emit('{"type": "message.new", "id": 123}');
// → EventEnvelope.fromJson 中 data['id'] as String? 抛出 TypeError
```

**状态**: deferred — 本轮严格限制仅修复 DEFECT-001（type 字段），不扩展修复范围。建议后续授权后按相同策略修复。

### DEFECT-003 (deferred): payload 字段使用 `as Map<String, dynamic>?` 模式

**位置**: `lib/core/realtime/event_envelope.dart` — `EventEnvelope.fromJson`

**描述**: `payload` 字段使用 `(data['payload'] as Map<String, dynamic>?) ?? {}`。如果服务端发送 `{"type": "valid", "payload": "not-a-map"}`，`as Map<String, dynamic>?` 会抛出 `TypeError`。

**状态**: deferred — 同上，建议后续授权后统一修复所有字段的类型安全问题。
