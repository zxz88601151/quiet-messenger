# 开发环境与部署策略（V1 冻结）

> 原则：不要"一上来就直接在生产服务器改代码"。开发与部署分离，服务器早接入但不当主开发环境。
> 来源：用户 2026-08-23 明确指示，Phase 0 阶段冻结。

---

## ❌ 禁止的开发方式
```
买服务器 → 直接在服务器写代码 → 改一点 → 重启 → 再改 → 再部署 → 发现问题 → 继续改
```
会把以下所有问题**混在一起**，后期极痛苦：
- 开发环境问题
- Python 环境问题
- PostgreSQL 问题
- Nginx 问题
- SSL 问题
- WebSocket 问题
- Flutter API 地址问题
- PySide6 打包问题

---

## ✅ 推荐：三层环境

```
                Git
                 │
       ┌─────────┴─────────┐
       ↓                   ↓
  环境 A：本地开发        环境 B：云服务器（测试/集成）
       │                   │
   快速改代码            验证真实网络
       │                   │
       └─────────┬─────────┘
                 ↓
           环境 C：正式生产（V1 完成后）
```

### 环境 A — 自己的电脑（主开发）
- Backend（FastAPI + SQLite 或本地 PostgreSQL）
- Flutter（模拟器 / 真机 USB 调试）
- PySide6（Windows 本机运行）
- 全部本地可跑，快速迭代。**这是主要开发环境。**

### 环境 B — 云服务器（阶段性集成测试）
- FastAPI + PostgreSQL + Nginx + HTTPS + WebSocket
- 用途：**阶段性**验证真实网络，不是日常开发。
- 重点验证：`手机 → Internet → 服务器 → Windows` 全链路，尤其 WebSocket(wss) 与 QR 登录真实网络。

### 环境 C — 正式生产
- V1 全部完成后才正式部署。不提前。

---

## ⏱ 服务器第一次接入时机（关键）
**不要等项目全部完成才部署。** 也不要一上来就当主开发环境。
推荐节奏：
```
Phase 0  架构设计
Phase 1  基础设施（本地跑通）⭐ 第一次服务器部署
Phase 2  账号（服务器验证）
Phase 3  好友（服务器验证）
Phase 4/5 聊天 + WebSocket（服务器重点验证）
Phase 6  QR 登录（真实手机 ↔ 服务器 ↔ Windows）
QA  →  正式发布（环境 C）
```
即：**Phase 1 本地跑通后，即做第一次服务器部署**，之后每个 Phase 在服务器验证一次。

---

## 🔥 最关键的服务器节点：Phase 5（WebSocket）
前面注册/登录/好友本地易验证，但到了：
```
手机 → Internet → FastAPI → WebSocket → Windows
```
必须真实测试，尤其是 **wss:// 经 Nginx → FastAPI**，不能只测 `ws://localhost`。

服务器 Phase 5 必测：
- Flutter `wss://域名` 经 Nginx 代理到 FastAPI WS
- 断线重连、离线消息补偿在真实网络下的表现
- 多端（手机 4G / Wi-Fi + Windows）实时同步

---

## 📱 QR 登录更应在服务器验证（Phase 6）
核心特色链路：
```
Windows 生成 QR → 手机扫描 → 服务器 → 手机确认 → 服务器授权 → Windows 自动登录
```
本地可开发（短轮询 2–3s / 90s 逻辑本地能跑），但**最终必须验证真实网络**：
```
Windows → HTTPS → 服务器 → 手机 4G / Wi-Fi
```
因为本地 localhost 无法真正模拟手机扫码经公网访问服务器的场景。

## 📋 各阶段"该提醒用户做什么"清单（冻结）

| Phase | 本地（环境 A）完成标志 | 需提醒用户在环境 B 做 |
|-------|----------------------|----------------------|
| 1 | 后端起得来、register→login 拿 token、双端空壳启动 | **首次部署**：FastAPI+Nginx+HTTPS+SQLite/PG 跑起来，确认公网可访问 `/docs` |
| 2 | 注册/登录/找回密码/资料/搜索全链路本地通 | 手机+Windows 经公网登录一次，验证 HTTPS 与 API 地址配置 |
| 3 | 好友增删改查本地通 | 两台真机（或真机+Windows）经服务器加好友，验证跨网络 |
| 4 | 会话+历史本地通 | 跨网络设备开聊、加载历史 |
| 5 | WS 本地 `ws://localhost` 通 | **重点**：`wss://域名` 经 Nginx 验证实时收发、重连、离线，必须真机 4G 测 |
| 6 | QR 轮询+exchange 本地通 | **重点**：Windows 出二维码→真机 4G 扫码→确认→Windows 自动登录，验证真实 HTTPS 链路 |
| 7 | 双端 UI 打磨本地完成 | 真机/真 Windows 最终视觉与操作验收 |
| 8 | 本地全链路 QA 通过 | 环境 B 全量回归（QR 重放/双电脑/Auth 吊销/WS 断线），再决定是否进环境 C |

## 配置约定（避免后期混问题）
- API 基地址：客户端从配置文件/环境变量读取，**不硬编码 localhost**（环境 A 用 `http://localhost:8000`，环境 B 用 `https://域名`）。
- 后端 `CORS` 在 Phase 1 即按环境配置，避免上线才发现跨域。
- WebSocket 地址：客户端按环境切换 `ws://` / `wss://`，不写死。
- 数据库：Phase 1 本地 SQLite 开发；环境 B 起 PostgreSQL，验证切换无方言问题。
- 迁移：Alembic 统一管理，环境 B/C 用 `alembic upgrade`，禁止手动改表。
