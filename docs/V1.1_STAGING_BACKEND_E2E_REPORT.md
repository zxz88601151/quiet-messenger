## 12. A → B（真实双向消息闭环 — WS 业务层）

**⚠️ 诚实判定: NOT IMPLEMENTED IN CURRENT DEPLOYMENT（非 FAIL）**

真实测试:
- E2E-B 建立 WS（Bearer 鉴权，收到 authenticated/ready）
- E2E-A 建立 WS，发送 `{type:"message.send", payload:{conversation_id, content, client_message_id}}`
- 观察: B **未收到 `message.created` 事件**（B 仅收到 authenticated/ready 帧）

根因（源码核实，非推测）:
- `backend/app/routers/ws.py` 第 13 行注释明确: "本文件仅基础设施，**不实现任何业务事件**（message.* / friend.* / conversation.*）"
- `_receive_loop` 第 141 行: 业务帧类型 `else: continue`（忽略，不广播）
- `backend/app/routers/conversations.py` 第 4 行注释: "严格不实现：WebSocket 实时推送（message.created / message.read / typing，属 Phase 5）"

**结论**: 当前 Staging 部署的 backend（Minimal Chat API 1.1.0-alpha，Phase 2C + 基础设施 WS）**未部署 WS 业务事件层**。A→B 实时消息闭环在当前版本不可用。这是**部署范围事实**，不是"实现了却坏掉"的 FAIL。REST Message 已 PASS（§10），实时推送属后续 Phase。

**判定: A → B (WS business) = NOT VERIFIED / NOT IMPLEMENTED**

## 16. Failures & Deviations（真实差异记录，不假绿）

### 16.1 DEVIATION-1: 已是好友后重复发请求 → 201（契约预期不同）
- E2E-A 与 E2E-B 已成为好友后，A 再次 `POST /friends/requests` (target=B) → **201**（而非契约隐含的"已是好友"类响应）
- 影响: 低。好友关系由 friendships 双向行保证，重复请求未破坏关系。但 service 未对"已是好友"返回明确语义（可能新建了 pending 请求或返回既有）
- **判定: DEVIATION（记录，非 FAIL）**。建议后续明确"已是好友"返回码（409 或 200 既有）。

### 16.2 DEVIATION-2: client_message_id 幂等重发 → 201（契约预期 200 幂等）
- 相同 client_message_id 重发 `POST /conversations/{id}/messages` → **201**（契约 §4 说"返回已存消息 200 幂等"）
- 影响: 中。客户端若依赖 200 幂等语义去重，可能重复插入本地 UI；但服务端 (conversation_id, client_message_id) 约束应保证唯一（需进一步确认是否真正幂等落库，非仅状态码差异）
- **判定: DEVIATION（记录，非 FAIL）**。建议 service 层对重复 client_message_id 返回 200 + 既有消息。

### 16.3 NOT IMPLEMENTED: WS 业务消息闭环
- 见 §12/§13。当前部署未含 message.created 广播层。这是部署范围事实，Phase 5 才要求。

**总结**: 无"实现坏掉"类 FAIL。2 处契约/实现偏差（DEVIATION），1 处未部署（NOT IMPLEMENTED）。全部如实记录。
