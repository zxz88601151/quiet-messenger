==================================================  
六、Alembic PostgreSQL 验证
=======================

使用真实 PostgreSQL 执行：

alembic upgrade head

然后验证：

1. migration 成功
2. 所有 8 张核心表存在
3. FK 正确
4. UNIQUE 正确
5. Index 正确
6. privacy_settings JSON 字段存在
7. Device 正常
8. QRLoginSession 表存在
9. messages 表不存在 status 字段
10. conversations 唯一约束正确

然后执行一次：

alembic downgrade

再：

alembic upgrade head

确认 migration 可逆并可重新建立。

注意：

如果 downgrade 会破坏已有 staging 数据，这是允许的，  
因为这是专用验证数据库。

但必须记录实际结果。

八、部署 Backend
============

创建最小生产化 Staging 部署结构。

允许新增：

backend/Dockerfile

docker-compose.yml  
或等价 Staging compose 配置

deploy/  
nginx/  
scripts/  
README.md

具体目录可根据现有项目结构调整。

要求：

- 不硬编码 JWT_SECRET
- 不硬编码数据库密码
- 不提交 .env
- .env.example 可以提交
- production/staging secret 不进入 Git
- Backend 不直接暴露公网业务端口
- Nginx 负责反向代理
- PostgreSQL 不直接暴露公网
- 使用健康检查
- Backend 启动失败时容器必须明显失败
- migration 必须明确执行
- 日志不能输出密码/token/secret

九、CORS
======

CORS 必须继续保持环境变量驱动。

禁止：

allow_origins=["*"]

Staging 使用明确来源。

例如：

CORS_ORIGINS=<https://staging.example.com>

如果暂时没有真实域名：

使用明确的 Staging 来源进行验证，  
不要为了测试永久打开 wildcard。
